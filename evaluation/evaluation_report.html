MMR Re-embeds Query & All Documents on Every Call
retrieval/mmr.py:24-26 — Redundant OpenAI API calls
Latency Cost
▼
What Was Observed
The MMR step calls embed_query(query) and embed_texts(doc_texts) again — even though the same query was already embedded in dense_search() and the same documents were embedded during ingestion. For 7 reranked chunks with text-embedding-3-large (3072-dim), this adds 300-800ms and ~$0.005 per query. 
# mmr.py:24-26 — CURRENT (redundant calls)
query_emb = np.array(embed_query(query))        # Already done in dense_search!
doc_texts = [d["text"] for d in documents]
doc_embs  = np.array(embed_texts(doc_texts))   # Re-embeds 7 chunks via OpenAI!

Pass pre-computed embeddings through the pipeline. Store the query embedding from dense_search and retrieve document vectors from Qdrant (they're already stored).
# Option A: Pass embeddings through the pipeline

    ...
) -> list[dict]:

# Option B: Request vectors back from Qdrant in dense_search
results = client.query_points(
    ...,
    with_vectors=True,   # returns stored dense vectors
)

Cold-Start Embeds 130+ Topic Strings via OpenAI
guardrails/topic_classifier.py:19 — 1-3s added to first request
Latency Cost
▼
What Was Observed
On the first query of each cold start, _get_topic_centroid() embeds 130+ topic strings from SADHGURU_TOPICS via OpenAI API. This adds 1-3 seconds to the first user's experience.
# topic_classifier.py:19 — 130+ strings embedded on cold start

def _get_topic_centroid() -> np.ndarray:

    if _topic_centroid is None:
        _topic_centroid = np.load("data/topic_centroid.npy")

Sparse Index Mismatch — Ingestion vs Query Use Different Schemes
ingestion/indexer.py:68-78 vs retrieval/sparse.py:25 — Sparse search is broken
Retrieval Quality Correctness
▼
What Was Observed
During ingestion, sparse vector indices are BM25 document-position scores (sequential integers 0..N). During query, indices are hash(token) % 50000. These are completely different index spaces. The sparse search is matching on random index collisions, not actual token matches. Half of hybrid retrieval is effectively noise.
# INGESTION (indexer.py:68-78) — indices are document positions
scores = bm25.get_scores(token_set)
indices = [j for j, s in enumerate(scores) if s > 0]  # j = 0,1,2,3...

# QUERY (sparse.py:25) — indices are token hashes
indices = [hash(t) % 50000 for t in token_set]       # hash = 7291, 43102...

# These NEVER align! Sparse search returns essentially random results.
Fix
Use the same hashing scheme at both ingestion and query time. Re-index after fixing.
# FIXED indexer.py — use consistent hash-based indices
from collections import Counter

tokens = text.lower().split()
tf = Counter(tokens)
unique_tokens = list(tf.keys())
indices = [hash(t) % 50000 for t in unique_tokens]
values  = [tf[t] / len(tokens) for t in unique_tokens]

point.vector["sparse"] = SparseVector(indices=indices, values=values)

# sparse.py:25 — already correct, no change needed
indices = [hash(t) % 50000 for t in token_set]

No Embedding Cache — Identical Queries Re-embed via API
ingestion/embeddings.py:48-57 — No LRU or memoization
Latency Cost
▼
What Was Observed
embed_query() is called multiple times per pipeline run: once in topic_classifier, once in dense_search, and once in MMR. No caching exists at the embedding level — every call hits the OpenAI API.
# embeddings.py:48 — no caching, calls API every time
def embed_query(text: str) -> list[float]:
    response = client.embeddings.create(model=..., input=[text])
    return response.data[0].embedding  # $0.002 per call, 150ms+
Fix
from functools import lru_cache

@lru_cache(maxsize=1024)
def embed_query(text: str) -> tuple[float, ...]:
    if settings.embedding_provider == "openai":
        client = _get_openai_client()
        response = client.embeddings.create(model=settings.embedding_model, input=[text])
        return tuple(response.data[0].embedding)
    model = _get_local_model()
    embedding = model.encode(text, normalize_embeddings=True)
    return tuple(embedding.tolist())  # tuple is hashable for LRU

New asyncio Event Loop Created Per Query
streamlit_app.py:368-372 — Overhead + potential resource leak
Latency Stability
▼
What Was Observed
Every query creates a brand new asyncio event loop, runs one coroutine, then closes it. This adds ~5-10ms overhead. If an exception occurs between new_event_loop() and close(), the loop leaks. The Groq SDK supports synchronous calls natively.
# streamlit_app.py:368-372 — unnecessary async ceremony
loop = asyncio.new_event_loop()
answer = loop.run_until_complete(
    pipe["provider"].generate(system_prompt, question)
)
loop.close()
Fix
# Option A: Use asyncio.run() (handles cleanup automatically)
answer = asyncio.run(pipe["provider"].generate(system_prompt, question))

# Option B (better): Use Groq's sync SDK directly
def generate_sync(self, system_prompt: str, user_msg: str) -> str:
    response = self.client.chat.completions.create(
        model=self.model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_msg},
        ],
        temperature=settings.groq_temperature,
    )
    return response.choices[0].message.content

Full Disk Cache Rewritten on Every Query
streamlit_app.py:409-410 — JSON serialization scales O(n) with cache size
I/O Latency
▼
What Was Observed
After every cache miss, _save_disk_cache() serializes the entire cache dictionary to JSON and writes it to disk. At 5000+ entries with full answer text and source chunks, this becomes a multi-megabyte synchronous write adding 100-300ms.
# streamlit_app.py:409-410 — writes entire cache every time
st.session_state.query_cache[cache_key] = result.copy()
_save_disk_cache(st.session_state.query_cache)  # dumps EVERYTHING to JSON

# _save_disk_cache writes full dict:
CACHE_FILE.write_text(json.dumps(cache, ...))  # O(n) serialization!
Fix
Switch to SQLite for O(1) inserts.
import sqlite3

CACHE_DB = "data/query_cache.db"

def _init_cache_db():
    conn = sqlite3.connect(CACHE_DB)
    conn.execute("""
        CREATE TABLE IF NOT EXISTS cache (
            key TEXT PRIMARY KEY,
            value TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
    conn.commit()
    return conn

def _save_cache_entry(key: str, value: dict):
    conn = sqlite3.connect(CACHE_DB)
    conn.execute(
        "INSERT OR REPLACE INTO cache (key, value) VALUES (?, ?)",
        (key, json.dumps(value))
    )
    conn.commit()
    conn.close()  # O(1) — only writes one row

def _load_disk_cache() -> dict:
    conn = sqlite3.connect(CACHE_DB)
    rows = conn.execute("SELECT key, value FROM cache").fetchall()
    conn.close()
    return {k: json.loads(v) for k, v in rows}
